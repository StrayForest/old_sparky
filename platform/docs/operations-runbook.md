## Runtime checks

```bash
systemctl is-active deadlock-api deadlock-worker deadlock-web nginx
systemctl --failed
journalctl -u deadlock-api -u deadlock-worker -u deadlock-web \
  --since -1h -p warning --no-pager
df -h /
```

API, web, PostgreSQL and Redis bind loopback; Nginx is the only origin listener. The platform connects directly to PostgreSQL on `127.0.0.1:5432`. The canonical production environment is a root-owned `0600` file; scoped service env files are generated by the renderer and are not edited manually. The retired legacy Telegram bot, its `sparkydb` database and host PgBouncer are absent and must not become platform dependencies. `deadlock-health-monitor.timer` performs the lightweight five-minute readiness, service, disk, memory, backup-age and certificate-expiry gate. `deadlock-maintenance.timer` runs the daily restore-verified backup and bounded non-backup retention workflow. The complete production perimeter proof is the SHA-locked operator workflow; run it after the exact release is active:

```bash
gh workflow run platform-production-as12-proof.yml \
  --repo StrayForest/old_sparky --ref dev \
  -f expected_sha=<exact-deployed-source-sha>
gh run watch <proof-run-id> --repo StrayForest/old_sparky --exit-status
```

It inventories listeners, checks forwarded-header trust, repeats the Cloudflare/Nginx/UFW parity gate and probes the origin externally. It is read-only, publishes no origin addresses, and fails on any HTTP response.

## Retention and disk safety

Retention policies keep:

| Data | Policy |
| --- | --- |
| production releases | newest 5; the service protects `current`, `previous`, the validated shared-venv origin and three static maintenance pins; release-only operator staging must pass the validated origin and every installed pin |
| local release artifacts | newest 5 matching release groups |
| verified DB backups | all backup-creating callers retain exactly the newest restore-verified pair after checksum, isolated restore and Alembic verification; backup-only rotates backup pairs and skips other retention; verify-existing never prunes ([policy](backup-retention-protection.md)) |
| Playwright results on the production/pre-production host | 7 days |
| GitHub Actions Playwright and CI evidence artifacts | 14 days |
| trusted live-QA generations | protect the active/current/previous source SHAs; remove only older inactive generations after exact identity checks |
| live-QA runtime provider payloads | the runtime installer retains current/previous/active source commits and every recursively referenced provider; it keeps no unreferenced additional payloads after successful installation or explicit retention apply; daily storage maintenance does not prune provider payloads |
| maintenance reports | newest 30 |
| systemd journal | 30 days, 256 MiB, 32 MiB files, preserve 5 GiB free |
| Nginx/system text logs | rotate at 50 MiB, keep 7 compressed files |
| failed-login `btmp` | rotate at 16 MiB, keep 2 uncompressed files |

It never deletes shared env/runtimes, upload staging, current/previous releases, active/source-protected live-QA generations or caches, business rows or canonical reports; backup failure stops pruning. Backup rotation is common to full maintenance and backup-only mode: after the new pair passes restore and Alembic verification, exactly that newest pair remains. Backup-only skips all other retention. The currently deployed unit changes only through the reviewed source release; see the [backup retention policy](backup-retention-protection.md). Live-QA cache pruning holds the machine-wide lock, requires an idle browser cgroup/user, accepts only root-owned non-symlink `runtime-<40 lowercase hex>` trees, retains the newest valid unprotected fallback, and treats keep as a hard cap rather than an age window.
The shared disk policy requires `max(5 GiB, ceil(10% of filesystem total))` free (the independent 5 GiB floor plus the 10% free/90% used limit); overrides cannot lower the floor or raise maximum use. Canonical `disk_ext4_image_v1` maintenance additionally needs that floor plus the 256 MiB lead and 576 MiB image after the temporary dump exists. Before `pg_dump`, include expected dump allocation if it shares the filesystem (`platform_backup_restore_drill._scratch_disk_image_required_free_bytes` and `_scratch_prepare_disk_image`; see the [backup/restore runbook](backup-restore-runbook.md)). The source-bound backup workflow defaults to `tmpfs_v1`, so it does not exercise this image gate. `--backup-only` uses the same verified one-pair backup rotation while skipping other maintenance categories. Admission fails closed.
The host sweep uses seven-day `--test-artifact-max-age-days` transient retention; GitHub Actions keeps machine-readable CI evidence for fourteen days. Keep workflow uploads at fourteen days and do not broaden host retention to match it. Application services write structured JSON to journald. Nginx owns request logs, so Gunicorn access logging is disabled to avoid duplicates; warnings, exceptions and slow/contended records remain. The worker baseline is `WARNING`; the API keeps `INFO` for lifecycle diagnostics. Journald is not forwarded to duplicate syslog. UFW stays in `ufw.log`; the 15-minute logrotate timer checks Nginx, rsyslog and `btmp`. These limits never justify suppressing 5xx or slow-request diagnostics.

This policy follows [systemd-journald](https://www.freedesktop.org/software/systemd/man/252/journald.conf.html) and [logrotate](https://man7.org/linux/man-pages/man8/logrotate.8.html), uses Nginx's supported [log-reopen operation](https://nginx.org/en/docs/control.html), and aligns records with the [OpenTelemetry log data model](https://opentelemetry.io/docs/specs/otel/logs/data-model/). Retain actionable events and never log secrets, following [AWS logging best practices](https://docs.aws.amazon.com/prescriptive-guidance/latest/logging-monitoring-for-application-owners/logging-best-practices.html).

Apply mode holds locks in fixed order—platform release operation, retained-load, source build output, then live-QA machine lock—to keep pointers stable and avoid install, rollback, build and browser deadlocks. Backup-only omits non-backup retention; it still rotates the backup set to the new verified pair. Cache compaction follows its [runbook](fallback-runtime-cache-compaction-runbook.md).

Retention does not recompute multi-gigabyte tree digests. Deletion requires the exact 40-hex name, matching manifest identity, root ownership, expected read-only modes, same-device types and non-escaping symlinks. Runtime reuse verifies the full digest. Deletion renames revalidated caches to hidden tombstones; a later run validates and reclaims interrupted tombstones. Dependent destructive cleanup is fail-closed: path, identity, lock and source prechecks must all pass in one controlled execution before mutation. Use checked return codes or single-program flow so a failed precheck cannot be followed by deletion through shell continuation. After partial cleanup/error, record completed exact paths, verify post-state before resuming and never repeat a completed deletion.

Apply the bounded sweep through the reviewed workflow after reviewing the `run-retention-preview` plan below; the generic diagnostics inventory is not an apply plan:

```bash
gh workflow run platform-production-storage-maintenance.yml --repo StrayForest/old_sparky --ref dev \
  -f confirmation=APPLY-PRODUCTION-STORAGE-MAINTENANCE -f expected_sha=<exact-source-sha-currently-deployed>
gh run watch <maintenance-run-id> --repo StrayForest/old_sparky --exit-status
```

Keep the workflow ref at `dev`; `expected_sha` is the active deployed app source. The run and both QA reports bind to current `dev`, while each report targets the app SHA and, if different, carries the authenticated `verified-noop` source-binding digest. Never use arbitrary SHA refs.

Storage diagnostics/maintenance workflow or exact storage-retention skill changes use the closed storage-operations route: full runtime-sensitive verification, no application/baseline action; AUTO takes its no-deploy branch. The recovery producer uploads a bound skip receipt with provenance attestation; the publisher checks fields against exact producer and parent CI/classifier evidence but does not verify the attestation cryptographically or publish a host bundle/production marker. When activation reports a full filesystem or unusable temporary directory, collect bounded read-only evidence before cleanup with `gh workflow run platform-production-storage-diagnostics.yml --repo StrayForest/old_sparky --ref dev -f expected_sha=<exact-source-sha-currently-deployed>`:
It reports filesystem/journal/service usage, generic report-only `release_retention_preview` candidates (`keep=5`, age 0, no unit pins), current/previous identities, latest restore-verified backup age/checksum and timer state; it compares installed/release-owned units and emits only drop-in presence. This is not the deletion set: `run-retention-preview` validates the loaded unit and derives a no-apply plan from its exact pin-bearing argv. Backup checksum reads are timeout-bounded. Diagnostics never mutate backups/files/settings; failure artifacts contain bounded partial evidence and closed outcomes, never raw host output. Maintenance evidence binds one invocation; a verified backup plus nonzero exit may follow deletions when thresholds fail, so failure proves neither no deletion nor successful cleanup.

The canonical maintenance service requests private typed backup diagnostics. If fresh backup or restore verification fails, it writes a root-owned mode-`0600` receipt in `shared/maintenance`, bound to that service invocation, active release source SHA and time window. The workflow projects only closed disk, memory-admission and restore fields; the service remains failed and produces no success report/retention proof, and backup failure stops pruning. Journals contain no exception text or receipt body; `report_keep` bounds receipts with success reports on the next successful run.

### Failed maintenance service in normal state

Preserve exact failure evidence before any systemd metadata reset. If `.release-operation.json`, `.release-systemd-state.json` or `.release-quiesce.json` exists, stop: use the documented source-bound recovery workflow, not this normal-state handling. The root-owned `shared/.release-recovery` directory is a persistent helper/archive store; its presence alone is not a pending-operation marker, and its contents must not be removed for acknowledgement.

An operator may acknowledge only an exact, independently reviewed failure with a narrowly scoped helper after explicit root approval and fresh canonical strict readiness immediately before invocation. That helper must verify current/previous release and unit identities, fresh source-bound operator evidence, idle jobs/processes and cgroup state, and the originally active+enabled maintenance timer under the canonical release lock. It may pause that timer and issue one `reset-failed deadlock-maintenance.service`; it must never start the service, alter release/database/config state, retry the reset, or treat the reset as a fix. Restore only the timer's original state, preserve the failure evidence, write a durable result, then run fresh canonical strict readiness and confirm timer restoration. An unknown cause remains unknown, and acknowledgement gives no QA credit; on refusal or failed postconditions preserve evidence and stop.

For emergency release-only staging, follow the [storage-retention skill](../../.agents/skills/platform-storage-retention/SKILL.md), passing the validated origin and every installed pin with `--protected-release`, then the complete reviewed candidate set with repeated `--expected-candidate` at apply. The skill has the exact preview/apply command and receipt steps. JIT-check candidate inodes, pointers, locks and pending transactions; never delete a protected identity. Apply the full sweep afterward only if its fresh preview retains the origin.

Preview live-QA runtime cache retention (also machine-locked and idle-gated):

```bash
/usr/bin/python3 -I \
  /opt/oldsparky/platform/current/tools/platform_live_qa_guard.py \
  prune-runtime-cache --keep 1
```

The preview is dry-run unless `--apply` and takes release then live-QA locks; the maintenance unit in this source tree uses the one-pair backup policy while running other retention and health checks. Backup growth is bounded to the newest restore-verified pair and the shared disk gate remains `max(5 GiB, 10% free)`. The rollout enables the timer only through the source-bound workflow after load/CPU/live-QA evidence passes. After enabling, let any timer-started service finish and confirm it is inactive with no operation locks before final diagnostics; do not weaken guards or blindly retry. After each run, follow `.agents/skills/platform-storage-retention/SKILL.md` for exact cleanup; never use broad deletion.

## Request-driven tournament updates

Ready Check and the bracket grid are request-driven. The tournament page
receives its schedule and initial bracket in the ordinary HTTP workspace
response. Ready Check transitions are local timer updates; the grid shows
passive bracket changes after a manual page reload. Explicit bracket mutations
may refetch the authoritative response needed to display the result.
When investigating stale tournament data, inspect ordinary API latency/status logs and ask the user to reload the page; there is no background tournament update mechanism to restore or tune.
Detailed retained-load cleanup, hermetic web verification and the exact source
address allowlist are maintained in the [retained-load and web verification
reference](retained-load-and-web-verification.md).

## Performance

Canonical load and latency budgets belong to the versioned profiles in
`platform/performance/profiles/` and are evaluated by
`platform/tools/platform_load_acceptance.py`. Keep this runbook focused on
measurement procedure and resource evidence rather than maintaining a second
threshold inventory.

Measure one user step before tuning. Capture response bytes, status/304 ratio,
p50/p95/p99, SQL/request, DB and compute time, pool checkout wait,
CPU/RAM/load, connections, locks, cache state, Celery queue backlog/retries and
worker lifecycle. Use
`tools/platform_production_qa.py --collect-performance` and
`tools/platform_performance_audit.py`; detailed JSON stays under shared storage.
For read-path diagnosis, distinguish checkout wait, connection hold, SQL and complete request time; see the [performance transport runbook](performance-transport-runbook.md) for attribution. The `connection_after_sql_time` diagnostic is `max(0, pool_connection_hold_ms - sum(db_sql_ms))`: held-connection time outside recorded SQL spans, not time after the last SQL statement. Workspace and `/users/me` release the session after materialization; exceptions still follow normal dependency teardown.
Reviewed production load profiles are JSON contracts under
`platform/performance/profiles/`, selected by ID in
`platform-production-external-load.yml`; this runbook covers procedure and
evidence, not profile parameters or acceptance thresholds.
Use a small smoke run first, then an average/human-shaped run; run stress or
breakpoint only in an approved low-traffic window and soak when leaks are
suspected. Keep functional success separate from thresholds; correctness can
still fail the latency/resource gate.
Do not increase Gunicorn/Celery workers, add PgBouncer, install exporters or
introduce a cache/schema rewrite without retained evidence. If both VPS cores
remain saturated after unnecessary work is removed, classify a capacity limit
instead of hiding it with more local workers.
Use the [tmpfs allocation diagnostic](../performance/README.md#host-tmpfs-allocation-diagnosis)
only in an authorized window; require its documented `COMPLETE_METADATA`
receipt criteria. Counters, names and totals do not prove ownership or permit
cleanup; obtain separate owner/lease and dependency evidence first. It has no
backup, retention, service, or deployment effects.

### Live production external load

For public capacity testing use the external-runner workflow, not a generator
running beside the API on the VPS. The workflow keeps fixture preparation and
exact cleanup on the origin, while the measured HTTP client runs on a
GitHub-hosted runner outside Cloudflare's origin network. It supports the
current `ready-vote`, `read-mix` and authenticated `page-load` profiles and collects a
parallel origin observer report. Temporary session/CSRF credentials are never
published as an artifact.
The [SSR capacity diagnostic runbook](ssr-capacity-diagnostic-runbook.md)
contains the exact zero-credit composite dispatch, source bindings, completion
criteria, and abort/cleanup commands. It sends the control account through
stdin; do not pass it in command arguments or environment variables. For all
retained-load operations, keep hosted-runner source and active app source
separate and satisfy the [retained-load cleanup contract](retained-load-and-web-verification.md).

To locate the concurrency knee, select `read-mix-concurrency-ramp-v1`. It
repeats the full 20,000-user route mix at concurrency 16, 32, 48, 64, 80, 96,
112 and 128, then performs the conditional refresh cohort. The report's
`phases.capacity_ramp.stages` entries are the comparison table; do not infer a
winner from the aggregate alone. `phases.capacity_ramp.analysis` marks the
first large p95 increase with a flat throughput gain as an admission candidate;
it is evidence for an operator-selected runtime profile, not an automatic
configuration change. This is a stress diagnostic, so bounded typed
authenticated-read shedding is counted separately from unexpected errors. Run
it only in an approved window and complete exact cleanup. Accept a Ready Check
knee only when all eight state guards pass with 40/40 active cohorts and
positive per-response deadline headroom; HTTP success alone is insufficient.
Before planning another matrix run, check [current state](CURRENT.md) and the
[performance matrix](../performance/README.md#current-11-profile-production-matrix);
do not repeat a completed or explicitly closed cell without a newly recorded
owner decision.

The SSR dependency graph has a hermetic browser contract in the platform web
smoke suite: an authenticated tournament page must call `/auth/bootstrap` and
must not call `/users/me` from the global layout. That test verifies ownership
of the request graph, not production latency. Select
`authenticated-page-load-v1` for the real external benchmark: it requests the
HTML route through `https://old-sparky.com` with a retained session cookie and
reports `time_to_first_byte`, complete page latency, HTML bytes and the
origin-side Next.js/API/DB observer. It is still a request benchmark, not
20,000 browser processes.

The selectable runtime A/B profiles are `uvicorn-classic`, `uvicorn-optimized`, `pool-pre-ping-off`, `authenticated-read-admission-32`, `authenticated-read-admission-24x8`, `authenticated-read-admission-24x8-native`, `web-ssr-diagnostics`, `web-ssr-native-transport`, `web-ssr-workers-2` and `api-pool-{12,16,20,24}`. Apply one at a time and restore the baseline; SSR diagnostics sample 1% of Next.js stages plus event-loop/Nginx timing and do not change SSR/CSP. The native transport profile changes only the trusted loopback auth GET implementation with one web worker; the combined `authenticated-read-admission-24x8-native` profile preserves the exact 24x8 admission tuple and changes only `PLATFORM_WEB_SERVER_AUTH_TRANSPORT` to `node`, enabling a reproducible runtime-profile A/B. The workers-2 profile combines that transport with two web workers and remains an explicitly measured candidate. The diagnostic profile pins the API to the public `INFO`/performance-logging selectors so fast auth rows remain visible, then restarts `deadlock-api` because its sampled auth/API log gate is read at API startup. Profiles that change startup-read SSR flags restart `deadlock-web` after applying the shared environment so the selected state is not left stale in the existing Next.js process. Readiness is checked for both services, and the restore path clears the diagnostic gate and logging selectors. The `pool-pre-ping-off` recovery test is mandatory.
Profile settings and their measured outcomes are owned by the
[performance evidence](../performance/README.md). Do not apply an experimental
profile based on historical runbook results; use the reviewed profile contract
and its required release, readiness and restore gates.

Before attributing a transport result to Nginx, record `nginx -v` and run
`nginx -t`. The named `platform_api` and `platform_web` upstreams have explicit
loopback keepalive; the HTML route clears `Connection` and does not advertise a
WebSocket upgrade. For database evidence,
collect `pg_stat_statements` query IDs, allowlisted statement categories,
total/mean execution time, rows and buffer hits/reads. Raw SQL text and
`pg_stat_activity.query` are never retained. The external observer excludes
only its own diagnostic queries, so SSR/read runs expose their actual numeric
top-statement aggregates. Also
record `pg_stat_activity.application_name` ownership totals for
`oldsparky-api`, `oldsparky-worker`, `oldsparky-qa`, `oldsparky-observer` and
`oldsparky-maintenance`; compare those totals to the 52 safety budget before
changing pool size. Use `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, MEMORY)` only on
a reviewed disposable or read-only query target.

The `/auth/bootstrap` SSR dependency validates session/roles against PostgreSQL
without writing `last_seen_at`: read-only page renders avoid an extra DB
checkout, while mutation-oriented dependencies retain normal touch behavior.
The `/users/me` account read-model is a short-TTL supplemental representation
for avatar and Steam/password flags; session validity, roles, credits and
authorization remain authoritative in PostgreSQL. Its monthly quota count is
refreshed on every cache hit because it is derived from tournament rows;
profile, identity, password, credit, role and tournament-creation commits
invalidate the representation. A Redis hit removes supplemental joins but not
the authoritative auth lookup or quota count. With `request_perf` diagnostics enabled, the account read-model emits low-cardinality Redis GET, async build-wall and Redis write-wall timings with bounded hit/miss/error outcomes. `build_ms` is wall time, not CPU time, and these spans do not cover the full route, SQL work or DB connection hold. Errors use the existing retention trigger; hit/miss events follow sampling. Events omit account IDs, Redis keys, payloads, revisions and timestamps.

The current candidate deliberately does not make public HTML static or bypass
the nonce CSP. Any future public/static route split requires a separate
measurement, security and caching design review; it must not be smuggled into
an SSR timing experiment.

### External fixture cleanup and runtime baseline

Run external workflows only in a low-traffic maintenance window; origin-side
fixture preparation, observation and exact cleanup remain separate from the
GitHub-hosted HTTP client described above.

The selected Ready Vote profile measures real vote POST contention after the
server-known window. It reports accepted/rejected votes, response latency,
database pool wait, lock pressure, API/PostgreSQL CPU and connections, and
duplicate/idempotency behavior. It exercises only vote POSTs; the timer phase
is entirely local. Clean the exact load run with the same cleanup workflow
before starting another production load.

The vote endpoint uses a deliberately minimal authenticated-session lookup: it
validates the session, user status and expiry but does not hydrate role data or
touch `last_seen` inside the burst. Authentication returns a detached user/time
snapshot through the route-owned short transaction; the auth lookup, ordinary
preflight, conditional upsert and commit therefore share one session checkout.
The ordinary preflight selects only the tournament columns needed by the vote;
ORM tournament hydration remains limited to lazy workflow transitions. Vote
authorization still performs the full server-side time, participant, profile,
round and workflow checks; ordinary authenticated requests retain role
hydration and session last-seen updates.

Ready Vote `request_perf` records low-cardinality spans for admission, auth, the
dedicated checkout (including `ready_vote_checkout_count` and
`ready_vote_checkout_ms`), preflight, conditional upsert, commit and response
construction. Admission fields include the process-local in-flight count and
limit, bounded admission wait, controller state/limit changes, smoothed CPU,
admitted/shed totals, pool wait and periodic CPU-monitor sample cost/count.
`ready_vote_upsert_ms` includes the
trigger-maintained counter work. The conditional upsert returns `changed=false`
for an identical choice, so it performs no vote-row update, counter delta or
cache invalidation. These fields are aggregated by route and QA phase by the
production QA parser; successful fast requests remain below the normal
per-request INFO logging path unless the existing slow-request/failure gate
selects them.

The structured production-QA summary exposes `ready_vote_cpu_pressure_percent`
with percent-labelled distributions and `ready_vote_count_metrics` with
count-labelled distributions. The older generic `*_ms` projections for these
fields remain in accumulated reports for compatibility and are deprecated;
they are not milliseconds. These values describe diagnostic samples or
process-local snapshots selected by the observer. In particular, CPU pressure
is a worker EWMA sample, and checkout/admission totals and controller changes
are snapshots or counters. Their summary distributions are not rates, deltas,
or time-weighted averages. Compare them only with matching observer windows
and report the sample population.

### Ready Vote admission contract

Ready Vote has a process-local controller in each Gunicorn worker. It performs
no batching and no Redis operation. A request takes a slot immediately while
the worker is below its current limit; the default admission wait budget is
`0 ms` with `0` waiters, so excess attempts receive a cheap `503` before
`ready_vote_db_session()` and perform zero checkout/SQL work. The response body
contains `code=READY_VOTE_OVERLOADED`, `retryable=true` and a bounded
`retry_after_ms` hint.

When a nonzero wait budget is configured, a waiter is admitted only if its
capacity slot becomes available before the deadline. A delayed event-loop wake
after the deadline sheds the request before it can acquire the slot or open a
database session. Cancellation while waiting removes the waiter registration
exactly once without counting the cancelled request as admitted or shed.

The reviewed code defaults are per worker: minimum `4`, initial `8`, maximum
`16`. Production is currently pinned by the runtime profile to static-8:
minimum/initial/maximum `8/8/8`. The controller smooths CPU samples every
`0.5 s` with EWMA
alpha `0.25`; `70%` is watch, `80%` enters pressure and `90%` is severe.
Latency, admission wait and DB pool wait are additional signals. Pressure
reduces the limit quickly, while recovery increases it one slot at a time only
after sustained healthy samples. Thus the aggregate effective concurrency is
the sum of the two independent worker limits and is intentionally not a global
Redis semaphore.

The browser treats this as one logical action: it enters `Подтверждение...`
immediately, ignores duplicate activation while pending, retries only the
explicit overload code at most twice with full bounded jitter, then shows a
temporary busy message and a short cooldown. Authentication, CSRF, validation,
eligibility, closed-round and other business errors are never retried.

Performance reports keep full-population HTTP client measurements separate from the diagnostic `request_perf` journal sample. The client summary covers every request issued by the QA phase; server request metrics include only lines selected by the existing slow-request/failure/diagnostic logging policy and must not be interpreted as a population count. Sampled API workspace requests may include the closed `diagnostic_activation` outcome: `plan_active_off`/`plan_active_on` means only that the request trace and plan matched an accepted phase, not that profiling or journal capture succeeded. Other values are bounded activation decisions such as an absent/invalid trace, no valid plan, run mismatch, or prearming; no trace ID or header value is logged, non-workspace requests omit the field, and aggregate counts cover only the selected sample.

The external Ready Vote fixture creates and joins every tournament before it
starts any Ready Check. This keeps the first tournament's ten-minute manual
window from expiring during sequential 20k setup, so the duplicate phase
measures idempotency rather than an already-closed round.

Retained users are provisioned with authenticated sessions rather than logging
in inside the burst. The harness derives the same session-bound CSRF token that
the login response issues, so `/auth/csrf` is not an artificial
first-mutation dependency in the write latency numbers; authentication/CSRF
endpoint load is covered by the ordinary read/auth profiles.

The helper binds that runner SHA and the separately checked active app SHA to the same root-owned marker and fixture-manifest digest; it verifies the credential-bearing manifest itself when that file is still present.

It confirms the selected run-owned processes are absent and the shared lock is clear.

An already-absent receipt requires two clean scans for the exact supervisor, observer and run-root helper processes, exact exit evidence and a clear lock.
The receipt keeps `namespace_closed: false`, grants no performance credit, and permits cleanup only after the workflow normalizer accepts it.

A missing run root with zero durable rows closes only when the current failed workflow attempt proves validation failed before fixture admission, all workload mutation steps were skipped, and exact host lock/process/path checks are clear; its receipt binds that attempt and source SHA and awards zero credit. ## Alert thresholds

- failed/restarted service;
- disk below `max(5 GiB, 10% of total capacity)` available or above 90% conservative use (the exact boundary is allowed);
- newest backup older than 24 hours or not restore-verified;
- sustained Celery queue growth or retry exhaustion;
- repeated 5xx/security delivery errors;
- sustained API 429/5xx responses or timeouts outside expected abusive traffic, especially with API/Redis resource pressure;
- p95 breach correlated with CPU, DB wait or lock evidence;
- Origin CA expiry inside the monitor threshold.
