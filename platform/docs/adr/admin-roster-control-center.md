# Admin roster control center

## Status

Accepted for the first admin roster vertical slice.

## Current architecture map

`TournamentDeadlockAssignmentRun.result_snapshot` is immutable solver
provenance. Publishing or locking a run materializes the current roster into
`TournamentTeam` and `TournamentTeamMember`. Team and bracket read APIs read
those normalized rows; Redis `teams`, `workspace_detail`, `bracket_summary`
and `bracket_full` entries are rebuildable projections. The existing
`/platform-ops` page calls the `/admin` API and remains behind the existing
authenticated session, application role checks, and Cloudflare Access.

## Decision

Roster administration uses intent-specific `/admin/tournaments/{slug}/roster/*`
commands. It does not expose generic CRUD or edit assignment JSON. Every
command locks `Tournament` first, then the current assignment run, teams,
members, participant rows and affected users in deterministic order. It
revalidates the lifecycle and expected state version while holding the lock,
mutates normalized live rows, recalculates starter strength with the shared
Deadlock formula, validates the complete resulting roster, writes a compact
audit event, and leaves commit ownership with the route.

The first policy permits ordinary admin corrections only for a published,
unlocked roster in `registration_closed` with no bracket matches. Locked or
bracketed rosters require an explicit superadmin override and reason. Any
live or completed match blocks roster mutations. Team keys and match topology
are never regenerated by member-only changes.

After commit, the route invalidates runtime caches and best-effort refreshes
the existing tournament read models. PostgreSQL remains authoritative if
Redis is unavailable. No new team, authentication, idempotency, or roster
history table is introduced; existing idempotency and audit infrastructure is
reused.
